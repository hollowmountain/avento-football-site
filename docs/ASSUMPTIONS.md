# Допущения

Неоднозначности ТЗ, решённые «разумным вариантом» (ТЗ §12).

1. **Уровень игрока в жеребьёвке.** ТЗ просит балансировать команды «по
   позициям и заявленному уровню», но форма вступления по ТЗ уровень не
   содержит. Добавлено необязательное поле «Ваш уровень» в форму записи
   (по умолчанию ANY = средний вес).

2. **Идентичность организатора для лимита «2 активные игры».** Организатор
   анонимен, host-токен уникален на игру. Лимит считается по тому же
   анонимному cookie-токену, что и у участников (`creatorTokenHash` в Game).
   Смена браузера/очистка cookie обходят лимит — по IP при этом действуют
   лимиты 3/сутки и 1/10 минут.

3. **Поздний отказ.** ТЗ в одном месте говорит «менее чем за 3 часа до
   старта», в другом — «после дедлайна отмены». Принято: поздний = после
   `min(cancelDeadline, startsAt − 3ч)`.

4. **Формула reliability.** «⭐ N%» = `100 × (1 − lateCancels/gamesJoined)`,
   меньше 3 игр — бейдж «🆕 новичок». Посещение засчитывается основному
   составу при переводе игры в FINISHED.

5. **Карта.** Интерактивный виджет не требовался — ссылка «Открыть на карте»
   (Яндекс.Карты по координатам).

6. **Ввод времени в форме.** `datetime-local` интерпретируется в таймзоне
   браузера организатора; таймзона игры берётся из `DEFAULT_TIMEZONE`.
   Если организатор создаёт игру из другой таймзоны, время на странице
   игры всё равно показывается в таймзоне игры.

7. **Дедлайн отмены по умолчанию.** Если поле не заполнено — `startsAt − 6ч`.

8. **Тихий отказ honeypot.** Ответ выглядит как настоящий успех (201 с
   правдоподобным кодом игры и токеном), игра не создаётся.

9. **Turnstile.** Написан за флагом `TURNSTILE_ENABLED` (verify через
   Cloudflare API), но без ключей вживую не проверялся. Обязательность
   «при превышении мягкого порога» не реализована — капча либо включена
   для всех созданий игр, либо выключена.

10. **Сортировка «мало мест».** Курсорная пагинация по (free, startsAt, id);
    поскольку свободные места меняются между запросами, при листании
    возможны редкие дубли/пропуски — для «живой» ленты это приемлемо.

11. **E2E-лимиты.** В Playwright-конфиге лимиты создания игр подняты
    (несколько игр с одного IP за прогон); сами лимиты покрыты
    integration-тестами и live-смоуком.

12. **Redis-ветка лимитера** (ZSET + Lua) написана по документации ioredis,
    но локально Redis отсутствовал — вживую проверен только PG-fallback.
    Первая проверка Redis-ветки случится на Railway при заданном REDIS_URL.
