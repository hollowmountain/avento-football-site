## Что уже построено

### Кабинеты (модуль `src/modules/profile`)

- `UserProfile`: уникальный тег (как в Telegram), ФИО, возраст, пол,
  код страны, любимый клуб, уровень игры, хеш личного кода.
- Пароля нет: устройство = анонимный cookie `kickoff_pid` (`ProfileDevice`),
  вход с нового устройства — по личному коду (показывается один раз,
  в БД только HMAC-хеш).
- API: `/api/me` (GET/POST/PATCH), `/api/me/login`, `/api/me/code`,
  `/api/me/tag` (живая проверка «свободен/занят»), `/api/me/games`.
- Кабинет `/me`: форма профиля, раздел «Мои игры» (созданные + где записан,
  роли «Организатор»/«Игрок»), личный код.
- Админ-теги через ENV `ADMIN_TAGS` (по умолчанию `ice` — тег владельца):
  создание игр без лимитов количества и без дедупа по месту.

### Публичные и приватные игры

- **Публичную игру создаёт только согласованный тег** (ENV
  `PUBLIC_GAME_TAGS`, по умолчанию `ice`): чужой человек не соберёт
  «открытую» игру и не обманет записавшихся. Остальным доступны
  приватные — `PRIVATE_LINK` (ключ в ссылке `?key=…`) и
  `PRIVATE_PASSWORD` (пароль от организатора).
- В ленте видны **все** игры; приватная помечена «Приватная», но запись
  без ключа отвергается (`JOIN_KEY_INVALID`, 403). Организатору ключ не
  нужен — он владелец.
- Ключ «по ссылке» хранится и открытым текстом (`Game.inviteKey`) —
  чтобы организатор мог поделиться ссылкой ещё раз; наружу он уходит
  только ему (`viewer.isHost`). Пароль хранится **только хешем**.
- `teamCount` теперь **1–4**: одна команда — «Сбор», встреча без матчей,
  у неё нет ни жеребьёвки, ни матч-дня.

### Игры (модуль `src/modules/game`)

- **Создавать игры может только владелец кабинета** (иначе 401
  `PROFILE_REQUIRED`); имя организатора берётся из профиля,
  игра хранит `creatorProfileId`.
- **Права организатора — по кабинету** (`application/host-auth.ts`):
  владелец профиля-создателя ИЛИ легаси host-токен. Секретный токен из
  интерфейса убран, но тихо сохраняется в localStorage для старых игр.
- `durationMinutes` nullable — «как получится» (расчёты берут 120 минут);
  `teamCount` 2–4; формат `FREE` («Свободный») по умолчанию.
- Запись на игру: имя + ник + «точно приду». Позиция и уровень не
  спрашиваются — уровень сервер берёт из кабинета.
- 5 уровней игрока живут в профиле (BEGINNER / AMATEUR / INTERMEDIATE /
  SEMI_PRO / PRO; ADVANCED — легаси, показывается как «Полупрофи»),
  веса жеребьёвки 1–5.
- Убраны из интерфейса: индекс надёжности, QR-код, фильтр по уровню в ленте
  (механика reliability в БД жива).

### Быстрая игра (`/quick`, модуль `src/modules/quick`)

Полностью клиентская, состояние в localStorage (`avento_quick_day_v1`).
2–4 команды, таймер, счёт, «Кто забил?» с автором и ассистентом, ротация
«победитель остаётся», **ничья решается суефа** (проигравшего выбирают в
диалоге), таблица дня, журнал с правкой счёта, шаринг текстом и
PNG-карточкой 1080×1350. `/quick/demo` — обучающий тур на 10 шагов.

### Рейтинг игроков (`/players`)

Все, у кого есть кабинет: место (`#1`, `#2`, …), ФИО, флаг, значок клуба,
тег, уровень, сумма «гол + пас» и её разбор с числом игр. **Порядок — по
сумме голов и передач**, при равенстве — по числу состоявшихся матчей и
алфавиту. Всё считает СУБД одним запросом
(`PrismaProfileRepository.listPlayers`): голы и передачи агрегируются
отдельными CTE, иначе join голов к составу размножил бы строки и испортил
счётчик игр. Сводится по `profileId` — гости без кабинета в рейтинг не
попадают. Проверено `tests/integration/players-rating.test.ts`.

### Карта в ленте

Переключатель «Список / Карта» в шапке ленты, дальше — Leaflet из npm с
тайлами OSM (`src/modules/game/presentation/games-map.tsx`). Ключей и
внешних SDK нет, карта грузится отдельным куском кода (`next/dynamic`,
`ssr: false`) и только когда её включили. Маркеры рисуются своим
`divIcon`, поэтому янтарь берётся из темы; в тёмной теме инвертируется
слой тайлов, но не пины. Клик по маркеру показывает карточку игры.
Домен тайлов добавлен в `img-src` политики CSP (`src/proxy.ts`) — без
него карта пустая.

### Матч-день внутри обычной игры

Страница `/games/<код>/day`, кнопка на странице игры появляется за два
часа до начала (`MATCHDAY_START_WINDOW_MINUTES` в `domain/matchday.ts`).
Протокол тот же, что в «Быстрой игре» — таймер, счёт, «кто забил» с
автором и ассистентом, ротация «победитель остаётся», ничья через суефа,
таблица дня, журнал матчей, — но состояние живёт в базе.

- Ведёт **менеджер**: по умолчанию создатель, он может передать день
  кому-то из записавшихся (нужен кабинет — права проверяются по нему,
  `isMatchDayManager` в `application/host-auth.ts`, поле
  `Game.managerProfileId`). Остальные видят то же самое, обновляются по
  SSE (`matchday_changed`), кнопок управления у них нет.
- Слои: `domain/matchday.ts` (правила и расчёты) →
  `application/matchday.ts` (команды дня) + `matchday-ports.ts` →
  `infrastructure/prisma-matchday-repository.ts` →
  `presentation/matchday-client.tsx` и `matchday-match.tsx`.
- **Ротация и таблица не продублированы**: `applyMatchResult`,
  `startRotation` и `computeStandings` берутся из `modules/quick/domain`.
  Формулы счёта в `domain/matchday.ts` описаны структурно (`ScoreSource`),
  поэтому работают и на сервере, и в интерфейсе поверх DTO.
- Все действия — одной ручкой `POST /api/games/:code/matchday` с
  разбором по полю `kind`, под блокировкой строки дня (`withDayLock`,
  тот же приём, что `withGameLock`). Ответ на любое действие — состояние
  целиком, клиенту нечего склеивать.
- Счёт матча — это его голы: отдельного поля счёта нет, расходиться
  нечему. Голы привязаны к участникам, через них — к кабинетам; из них и
  считается рейтинг.
- Завершение дня ставит игре статус `FINISHED` (состоявшаяся игра идёт в
  счётчик матчей рейтинга).

### Правки по замечаниям владельца (14.08)

- **Выход из кабинета** (`POST /api/me/logout`): устройство отвязывается,
  профиль остаётся. Диалог прямо предупреждает — без личного кода доступ
  пропадёт навсегда.
- **«Без клуба»** отдельной плиткой в палитре: выбранный клуб снимается.
- **Правка игры** организатором — диалог «Редактировать» (название,
  описание, время, площадка, адрес, вместимость, цена); PATCH на сервере
  был давно, не хватало интерфейса.
- **Удаление участника** организатором
  (`DELETE /api/games/:code/participants/:id`): место освобождается,
  первый из очереди поднимается, репутацию удалённому это не портит.
- **Шаринг**: чистый адрес игры (с ключом для приватной) плюс название,
  время и место отдельными строками — раньше уходил адрес текущей
  страницы со служебными параметрами.

## Что делать дальше

### 1. Личная статистика в кабинете `/me` (не начато)

Сыгранные матчи, голы и ассисты того же человека — из тех же данных, что
и рейтинг: `DayGoal` → `Participant.profileId`. Считать в SQL, как в
`listPlayers`, а не тянуть голы в память.

### 2. Что можно доделать в матч-дне (по желанию заказчика)

- **Переименование команд** прямо в протоколе: команда `renameTeam` в API
  готова, кнопки в интерфейсе нет.
- **Правка счёта сыгранного матча.** В `/quick` она есть (журнал с
  плюс-минусом), в матч-дне нет: счёт складывается из голов, и менять его
  отдельно — значит развести счёт с авторами. Пока лечится отменой
  последнего гола во время матча.
- **Карточка дня картинкой** (как `share-card.ts` в `/quick`).

### 3. Мелочи, замеченные по дороге

- Число команд дня берётся из `Game.teamCount`, а он задаётся при
  создании игры. Менять его в идущем дне нельзя — если понадобится,
  это отдельная команда протокола.
- Опоздавший, записавшийся уже после старта дня, в составе появится
  (`assign` заводит участника), но сам себя в команду не поставит —
  это делает менеджер.

## Перед показом друзьям — известные риски (не баги, но кусаются)

Владелец собирается дать сайт потыкать друзьям. Что стоит починить или
хотя бы знать заранее.

**Пункты 1 и 2 починены** (коммит «квота создания игр по кабинету и
автозапись организатора»):

1. ~~Лимит создания игр считается по IP~~ → квота считается **по
   кабинету**: `RATE_CREATE_GAME_PER_10MIN` и `RATE_CREATE_GAME_PER_DAY`
   теперь на профиль, а по IP остаётся широкий суточный потолок
   `RATE_CREATE_GAME_IP_PER_DAY` (по умолчанию 20) против ботов.
   Друзья с одного Wi-Fi друг другу больше не мешают.
2. ~~Создатель не записывается в игру автоматически~~ → в форме создания
   есть галочка **«Я тоже играю»**, включённая по умолчанию. Организатор,
   который только собирает игру, снимает её сам. Неудачная автозапись не
   отменяет создание игры.

Что осталось знать:

1. **Минимум игроков по умолчанию 2** — игра, где кроме организатора
   никого нет, отменится сама к дедлайну. С автозаписью создателя нужен
   всего один товарищ, но один всё же нужен.
2. **Потеря профиля.** Кабинет привязан к cookie браузера; личный код
   показывается один раз. Почистил данные сайта и не сохранил код —
   профиль недостижим (восстановление по почте отложено).
3. **Геокодер Nominatim** ищет координаты по адресу. Кривой адрес →
   «Не удалось найти это место», игра не создастся. Плюс у сервиса есть
   свои лимиты на частоту.
4. Старые игры, созданные до кабинетов, имеют `creatorProfileId = null` —
   ими можно управлять только по host-токену из localStorage. Матч-день
   в такой игре тоже доступен только по host-токену.
5. **Тайлы карты** ходят на `tile.openstreetmap.org` — это единственный
   внешний адрес, который теперь запрашивает страница. У OSM свои лимиты
   на частоту; если карта понадобится под нагрузкой, нужен свой источник
   тайлов (и его домен в `img-src`).

Проверено вручную (13.08): жеребьёвка и отмена игры работают через
кабинет БЕЗ host-токена — `POST /api/games/:code/teams/shuffle` и
`DELETE /api/games/:code` отвечают 200 при одной лишь cookie владельца.

## Грабли, которые уже съедены (не наступать)

- Имя цветового токена Tailwind не должно начинаться с имени встроенной
  палитры (`--color-amber-ink` → `bg-amber-ink` молча не компилировался).
- Реакт-хуки линт строгий: нельзя `Date.now()`/чтение localStorage в
  рендере (только lazy `useState(() => ...)` или обработчики); нельзя
  `setState` синхронно в effect (для «после гидратации» —
  `useSyncExternalStore`, пример: `src/shared/hooks/use-host-token.ts`);
  нельзя менять переменную замыкания внутри `.map()` (React Compiler,
  `react-hooks/immutability`) — писать обычный `for`.
- Одноразовый код держать в state СТРАНИЦЫ: `invalidate(['me'])`
  размонтирует форму, и код исчезает с экрана.
- Скриншоты снимать Playwright-скриптом, **дожидаясь конца анимаций**:
  `.page-enter` и диалоги стартуют с `opacity: 0`, Playwright считает их
  видимыми и снимает пустой кадр. Ждать
  `el.getAnimations().map((a) => a.finished)`.
- `waitForURL(/\/games\//)` совпадает и с `/games/new` — использовать
  `/\/games\/AVA-/`.
- Rate limit кусается в прогонах: 1 создание игры за 10 минут с IP
  (админ-тег `ice` обходит).
- **Дефолты «со сдвигом назад от даты» проверять на ближних датах.**
  Свежий баг (коммит 4aeaa47): дедлайн отказа ставился «старт минус
  6 часов», и для игры, назначенной раньше чем через 6 часов, он уходил
  в прошлое — фоновая уборка отменяла игру сразу после создания
  (`CANCELLED_NOT_ENOUGH`), по ссылке она открывалась, а из ленты
  пропадала. Лечит `defaultCancelDeadline` в `domain/game-rules.ts`
  плюс проверка в `createGame`. Тесты на это есть в
  `tests/unit/game-rules.test.ts`.
- В названиях команд кириллическая «А»: `Команда А` / `Команда Б` —
  Playwright-селектор с латинской `A` не найдёт ничего.
- В русских текстах не согласовывать глагол с названием команды
  («Жёлтые остаётся» — плохо), писать «На поле остаётся команда {name}».
- **Время в SSR-разметке.** Всё, что зависит от «сейчас», до гидратации
  обязано рендерить стабильное значение — иначе React пересобирает дерево
  и в консоли висит hydration mismatch. Таймер матч-дня до гидратации
  показывает только накопленное время (`useHydrated`,
  `src/shared/hooks/use-hydrated.ts`).
- **Playwright считает и скрытые узлы.** React оставляет копию разметки в
  служебном буфере стриминга (`div#S:0` вне `<main>`), и `toHaveCount`
  ловит её вместе с настоящей — счётчики удваивались через раз.
  Селекторы в e2e ограничивать `main`, а не искать по всей странице.
  Пользователь этот буфер не видит: он скрыт и живёт доли секунды.
- **Тег `ice` в локальной базе уже занят** (профиль «Апельсин Игнасьев»),
  так что скрипты прогона не могут просто взять админ-тег: заводите
  профиль с уникальным тегом на каждый прогон. Лимит создания теперь
  считается по кабинету, поэтому свежему профилю квоты хватает, а дедуп
  по месту обходится уникальным адресом при `GEOCODER=stub`.
- Деплой на Railway уже настроен, но если снова полезут ошибки:
  Railway подставляет контейнеру `PORT=8080` — своя переменная `PORT=3000`
  это перебивает; фиктивный `ENV` в Dockerfile обязан стоять ДО
  `npx prisma generate`; дерево CLI миграций должно лежать в
  `/app/node_modules` (конфиг импортирует `prisma/config`).

## Проверка перед сдачей любой задачи

1. `npm run lint && npm run typecheck && npm run test` — зелёные.
2. `npm run build`, затем `npx playwright test` — e2e зелёные.
3. Ручной прогон Playwright-скриптом + скриншоты (мобильный 390px и
   десктоп, тёмная и светлая темы), скриншоты прислать пользователю.
4. Коммит и пуш; дождаться деплоя и проверить прод по адресу выше.
